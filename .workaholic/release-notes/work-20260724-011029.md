# Honor or refuse a where predicate, never drop it silently

## Summary

A query stage that cannot be honored must never be silently ignored. The sharpest case was hit in production use on 2026-07-23: `where id == '<fileId>'` on a Google Drive folder listing returned the **complete unfiltered listing at exit 0**, so the predicate had no effect while the answer read as "these rows matched". This release closes that seam and the three siblings it admitted. **This changes behaviour that was previously a silent success** — several statements that used to answer now refuse.

## Key Changes

- The read executor re-applies the pushed `where` over every batch a facet returns; a facet opts out only by declaring `honors_pushed_filter` and applying its own truthful residual. Gmail and Drive had *computed* the residual and then discarded it — that was the reported defect
- An unknown column in a caller-written `where` is refused instead of matching nothing, so a typo and a legitimate empty result are finally distinguishable by exit code
- `expand` propagates `NotExpandable` for a Json/scalar column and `UnknownColumn` for an absent one, instead of passing the row through unchanged
- A codec source reports an undetermined schema, so the error names the true post-decode columns rather than the pre-decode blob
- The two facets that had opted out **unchecked** — `/s3`, `/r2` and the `/cf` KV/queue/artifact branches — now check too; the `/s3` object-download branch had been ignoring the predicate entirely

## Changes

### Changed
- Read execution re-applies the pushed filter unless the facet declares it honors it; `/sql`, `/cf`, `/ga`, `/mail`, `/drive` apply their own residual
- `where` and `expand` refuse an unknown column with a structured `ErrorKind::Usage` error (exit 2); empty and late-bound schemas stay lenient
- `PlanSource::Codec` reports an undetermined schema so post-decode errors name real columns
- `docs/cookbook/github.md` rewritten against the driver's real schemas — a fabricated column set, a non-existent `review_requests` path and a collection-addressed `call github.merge` are gone; `CALL github.comment` becomes the real `INSERT INTO .../comments`
- Five in-repo claims retracted that asserted the pre-release behaviour (a codec helper's doc, two test names, two guide pages, three "pass-through codecs" statements, and a blueprint claim that the schema is known at every seam)

## Upgrade Notes

**Behaviour change, deliberately.** Statements that previously succeeded silently now refuse:

- `where <unknown-column>` — was `rows: []` at exit 0, is now a structured refusal at exit 2
- `expand <json-or-scalar-column>` and `expand <absent-column>` — were no-ops, are now structured refusals
- A `/drive` or `/mail` listing with an unpushable predicate now actually filters, so results that were previously over-broad will shrink to the rows that really match

Six recipes in the GitHub cookbook were teaching columns the driver never had; they would have become exit-2 refusals under this change and are corrected here. The plugin is bumped **minor** (0.16.0 → 0.17.0) so installed skill caches pick up the corrected article.

`select` on an unknown column is **still** silently dropped — the last member of this family. The developer ruled on 2026-07-26 that it should refuse; that lands separately, sequenced after the cookbook ratchet is raised from parse-only to a typecheck.

## Known Gaps

- The cookbook ratchet only proves a recipe **parses**, which is why six recipes naming non-existent columns shipped green. Raising it to a typecheck against the compiled describe registry is ticketed at `20260725143000`
- `docs/cookbook/faq.md` describes exit 2 as "parse or CLI usage error" and lists neither `unknown_column` nor `not_expandable` — ticketed at `20260725143100`
- `check_of_assertion` compares against the empty codec schema without the leniency the sibling folds got — ticketed at `20260725143200`
