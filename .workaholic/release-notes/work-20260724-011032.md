# Enforce policy on the serve read path so a principal sees only what a grant allows

## Summary

The policy gate was inert on data reads: a pure `SELECT` lowered to an empty commit plan, the enforcer had nothing to adjudicate, and every readable path stayed readable by everyone regardless of policy. This release makes the serve read path evaluate `SELECT` against the endpoint's resolved policy under the real actor **before any driver scan**, proves every grant axis admits the matching actor and denies the non-matching one on reads, and proves fail-closed denial. **This is a hard break**: an endpoint with no attached policy now answers 403 where it previously returned rows.

## Key Changes

- Reads are gated: `evaluate_reads_with_context` adjudicates every scan target as `SELECT` under the request's resolved principal, sharing `decide_effect` with the write walk so the two can never drift into different notions of a grant
- A real defect fixed along the way: the request-time gate resolved policy by endpoint **name** while registration used the endpoint's policy **ref**, so a policy not named after its endpoint applied at registration and silently not at request time
- Fail-closed proven across three shapes — no policy denies, a dangling policy ref denies, and an anonymous caller sees only `Anyone`+`Always` grants — with a denied read returning a structured 403 problem body carrying no rows, no schema and no secret markers
- Every grant axis proven to bite on reads in both directions: `FOR` user/role (including inherited `owner ⊃ member`)/group, `AT ScopeGlob`, `WHERE member_of`, deny-precedence, and a federated read denying on its weakest leg

## Changes

### Changed
- The serve read path evaluates SELECT against the endpoint's policy before any driver scan; `CompiledRoute` now carries the endpoint's policy ref rather than resolving by name
- Taught surface corrected: `create policy … FOR user alice` is the statement spelling (the colon form `user:alice` is only the stored `/sys/policies` rule-string label, and the two are not interchangeable)
- `watchtower.qfs` fixture and two blueprint claims corrected — they asserted the opposite of the law this release enforces
- Five policy-less endpoint recipes in the query cookbook gained policy clauses

## Upgrade Notes

**Breaking.** Any `CREATE ENDPOINT` without an attached `POLICY` now denies reads with 403 instead of returning rows. Attach a policy to every endpoint you expect to serve. A scheduled job whose query is a pure read against a policy-less endpoint becomes permanently denied and re-fires on every sweep — the sweeper has no back-off, so review scheduled reads before upgrading.

The plugin is bumped **minor** (0.15.0 → 0.16.0) because the shipped cookbook recipe `create endpoint … as …` with no policy now denies; installed skill caches need the bump to pick up the corrected article.

## Known Gaps

- The statement bridge's read leg (`POST /api/run` with `mode=read`) still resolves no policy and runs under a hardcoded anonymous principal — strictly wider than the endpoint face this release closed. Pre-existing, mitigated only by the loopback-only default bind, which is a deployment posture rather than an authorization control. Tracked at `20260725110500`, with the developer's ruling recorded: it gets its own named policy row, failing closed when absent or dangling.
