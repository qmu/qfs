# ENCODE form makes a form-parameter REST API writable through a declaration etc

## Summary

A declared driver could read a plain-REST API but not write to one, because every declared write sent
a JSON body. `ENCODE form` adds the missing `application/x-www-form-urlencoded` encoder, so the
shipped Chatwork message `INSERT` commits instead of answering `400`.

## Key Changes

- `ENCODE form` renders a row's scalar fields as percent-encoded `k=v&k=v` and sets the content type,
  with no service-specific code.
- Unencodable fields are refused rather than guessed: a bytes, array, or nested-struct field returns a
  structured error naming `ENCODE multipart`, and a null field is omitted rather than sent empty.
- The shipped `chatwork.qfs` message map and its cookbook article now publish a statement that
  commits, confirmed against the live API.
- A `204 No Content` read is a successful empty result instead of a decode failure, so a correct path
  no longer reports as invalid.

## Changes

### Added
- `ENCODE form`, the generic form-urlencoded wire-body encoder for declared writes.

### Changed
- The shipped Chatwork declaration and cookbook article use `ENCODE form`.
- A `204 No Content` response decodes as zero rows; a malformed `200` body still fails.
