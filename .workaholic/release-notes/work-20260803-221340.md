# The Chatwork room-messages readings each get their own name

## Summary

The shipped `/chatwork` driver's `…/messages` view asked Chatwork for a room's *unread* messages, so
a second read of the same room came back empty. It now asks for the room's latest messages on every
read, and the unread-only reading keeps its own path.

## Key Changes

- `/chatwork/rooms/{room}/messages` passes `force=1`, so every read of a room answers the same
  question instead of only the first one.
- A new `/chatwork/rooms/{room}/messages/unread` view keeps the unread-only reading addressable
  rather than deleting it, and the cookbook says which of the two consumes what it returns.
- Two hermetic tests pin the behavior at the wire level, one driving the shipped declaration bodies
  through the real read facet and asserting the built request URLs.

## Changes

### Changed

- The declared Chatwork messages view returns the room's latest messages on every read; existing
  queries keep working and simply stop going empty on a second read.

### Added

- `/chatwork/rooms/{room}/messages/unread`, the API's cheap unread-only call under a name that says
  it consumes what it returns.

## Upgrade note

An operator with an existing `/chatwork` mount must re-install `chatwork.qfs` for the fix to reach
them — the install is a local previewed write with no network. Nothing detects a stale installed
declaration yet.
