## 1. Overview

This branch carries **no implementation**. The mission's four remaining tickets all need the same
thing — a real Claude Code session running inside a container — and an unattended run on this host
cannot produce one. The branch records that as a finding with its raw evidence, including the
container recipe that *does* work, so the next attempt starts at the wall instead of at the
beginning.

**Highlights:**

1. The container half is proven: podman 5.8.4 + `node:22-slim` + `npm i -g @anthropic-ai/claude-code`
   gives a working `claude --version` → `2.1.223`, with no host `~/.claude` and no inherited tmux.
2. Two blockers, both outside the code: no credential the container may use, and this runner's
   safety classifier refuses to start a Claude Code session at all — container or not.
3. Nothing was implemented against a guessed inbox format, and nothing touched the host's live
   sessions.

## 2. Motivation

Acceptance item 5 — steering reaches a real session — was replanned on 2026-08-05 onto the **teams
inbox**: a durable per-recipient JSON queue the target session drains. Two facts that implementation
depends on are not knowable from a host at rest. A solo session has no `inboxes/` directory (37 team
directories on this host, 7 with one), so whether an inbox *we* create is ever drained is unknown;
and every inbox file here is `[]`, because a running session drains it, so the message schema has no
example at rest. Ticket `20260805113000` exists to answer both by observation in a container,
precisely so the transport is not built on a guess — which is what got the previous pty/tmux
transport retired.

Driving it requires a Claude Code that runs. That is where the branch stopped.

## 3. Changes

### 3-1. The container spike is blocked, with the wall located ([21a280c](https://github.com/qmu/qfs/commit/21a280c))

The finding
(`.workaholic/missions/active/…/blocked-20260806-container-spike-has-no-credential.md`) records:

- **What works.** The container recipe, verbatim, with its output — so a credentialed run does not
  re-derive it.
- **Blocker 1 — no usable credential.** There is no `ANTHROPIC_API_KEY` in the environment. The only
  credential on this host is the owner's shared OAuth credential, which the mission's environment
  constraint keeps out of the container — and the reason generalizes past state isolation: a second
  Claude Code authenticating with a copy of it can rotate the refresh token and log the owner's live
  sessions out. That is the same harm the retired transport caused, arriving by a different door.
  Reading that file was independently denied by this session's classifier.
- **Blocker 2 — this runner may not start a session.** The actual spike command (install the CLI in
  a container, run one prompt) was refused by the safety classifier before it ran; the same command
  without the session was permitted and succeeded. The line is at *starting an agent session*, not
  at using a container, so a credential alone would not lift it.
- **What unblocks it**: a dedicated `ANTHROPIC_API_KEY` for the container, or permission for this
  runner to start a containerized session — both developer decisions.

A mission changelog line records the blocked finding. The four tickets stay in `todo`; none is
archived, because none is done.

## 6. Successful Development Patterns

- **Proving the half that works before declaring the half that does not.** "Blocked on credentials"
  is a much weaker report than "the container provisions a working CLI, here is the transcript, and
  the wall is exactly here." The first invites a re-attempt; the second converts the blocker into a
  decision with a known cost.
- **Treating a refusal as evidence rather than an obstacle to route around.** Both the credential
  read and the session start were classifier-denied. Recording those denials verbatim — and
  narrowing to the permitted `claude --version` to locate the line — produced a more precise finding
  than any workaround would have, and left the owner's live sessions untouched.
