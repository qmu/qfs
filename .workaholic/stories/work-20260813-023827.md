## 1. Overview

The Slack cookbook told a reader the three `qfs` commands that seal a token into the vault and bind
it to a mount, and never said where that token comes from. This branch adds the missing half — what
you create in Slack before any of it works — and corrects the article's scope table against the
declared driver, which turned out to disagree with it in both directions.

**Highlights:**

1. A new `## What to create on the Slack side` section before Setup: create the app, grant the bot
   scopes, install, copy the `xoxb-` token, and **invite the app to the channels it must read**.
2. `Scopes at a glance` became a capability→scope table of **eleven** rows verified one by one
   against the Web API method each path actually calls — up from three, two of them incomplete.
3. Verifying those rows exposed three documented operations with **no implementation at all**;
   that became its own ticket rather than a silent fix.

## 2. Motivation

`docs/cookbook/slack.md` opens its Setup with `printf '%s' "$SLACK_TOKEN" | qfs account add slack`.
Nothing on the page, and nothing in `docs/guide/connect.md`, said what `$SLACK_TOKEN` is or how a
person obtains one. The article's only vendor-console passage — *Post as yourself (a user token)* —
documents the `xoxp-` path and opens on "On the Slack app config (api.slack.com/apps) add the User
Token Scopes you need", which presumes the app already exists. For the ordinary case, adding a
workspace, the article started one step too late.

The gap has a sharp edge beyond inconvenience. A Slack app that holds `channels:history` still reads
nothing from a channel it was never invited to: the scope grants the ability to read history, not
membership of any channel. Slack answers `not_in_channel`, and from the outside that is
indistinguishable from the missing-scope case the article already documents — both are "a read that
comes back with nothing". A reader hitting it had no way, from this page, to tell the two apart.

The article is also the generation source for `plugins/qfs/skills/qfs-slack/SKILL.md`, so every gap
in it is a gap in what an agent knows.

## 3. Changes

**The new section** walks the console in Slack's own labels — **Create New App** → **From scratch**,
**OAuth & Permissions** → **Bot Token Scopes**, **Install to Workspace**, **Bot User OAuth Token** —
with the observable result named at each step, then hands off to the existing Setup block for the
`qfs` side. It closes with the two things a second workspace needs (its own account label, its own
mount path) and the reversal of the whole grant: uninstall or revoke on the Slack side,
`qfs disconnect` and `qfs account remove` on the qfs side. Both verbs were checked against `--help`
before being written.

**The invite requirement** rides a `::: warning` container stating cause and symptom together: the
tail read is `conversations.history`, Slack answers `not_in_channel` for a non-member app, so an
uninvited app and a missing `channels:history` look alike, and the invite is the cheaper of the two
to check first.

**`Scopes at a glance`** was three rows, of which the third — "read the channel tail on that mount:
`channels:history`" — was the article's only answer for every read it teaches. Reading
`slack_driver.qfs` view by view produced the real mapping: `channels:read` for the channel listing
and for resolving a `#name` in a `CALL`, `users:read` for the user directory and the DM peer lookup,
`im:write` to open a DM and `im:history` to read one, `files:read` for the file listings,
`reactions:write` and `pins:write` for those CALLs. Eleven rows, each traceable to a method the
driver names, plus a note that private channels are the separate `groups:` family.

**`docs/guide/connect.md`** gains one sentence in *GitHub & Slack — a token* pointing at the new
section, keeping the walkthrough in the cookbook where that page's own convention puts it.

The plugin moves `0.19.0 → 0.19.1` across all four fields (skill-affecting, no taught surface
retired) and the binary `0.0.96 → 0.0.97`.

## 4. Outcome

A person adding a Slack workspace can now go from "I have a Slack account" to a channel tail that
returns rows without leaving the qfs docs, and knows which of the two silent-failure causes to check
if it doesn't. An agent loading the `qfs-slack` skill gets the same text verbatim, including the
scope table it needs to tell a user what to grant.

## 5. Concerns

**The live verification in the ticket's Quality Gate has not been done, and this PR does not claim
it.** The gate asks for the section to be walked in a real workspace with the tail read observed
before and after the invite. Creating an app needs a browser session at api.slack.com, and reading
the already-connected mount on this machine needs the vault passphrase — `qfs run` on
`/slack/qmu/general/messages` returns `slack_auth`. The `not_in_channel` claim is therefore sourced
from the driver's own `conversations.history` call plus Slack's API contract, not from an observed
run. The ticket stays in `todo/` for that reason and the unit is a handoff.

**The article still teaches three Slack file operations that do not exist.** Verifying the scope
table against the declared driver showed the download (`/slack/<ws>/files/<id>` returning `content`),
the upload (`UPSERT INTO /slack/<ws>/files`), and the detach (`remove …`) have no view and no map
anywhere in the tree — the compiled driver that implemented them was deleted when `/slack` became
declared-only, and the twin's equivalence tests cover the file *listings* only. Out of this ticket's
scope, so it is now ticket `20260813024753`, which also has to decide the direction (reimplement in
the declaration, or remove from the article) before anything changes. The new scope table
deliberately carries no `files:write` row for the same reason.

## 6. Successful Development Patterns

**The driver asset is the only honest source for a scope claim.** Each declared view names the Web
API method it calls, so "which scope does this path need" is a lookup, not a recollection. Reading
`slack_driver.qfs` end to end is what turned a plausible two-scope answer into eleven verified rows —
and, in the same pass, what surfaced three documented operations with nothing behind them. A scope
table written from memory would have been wrong in both directions and looked fine.

**Check what the gate cannot.** The cookbook ratchet extracts only ```` ```qfs ```` fences, so a
section of prose and shell blocks has zero automated coverage; and VitePress runs with
`ignoreDeadLinks: true`, so a wrong anchor fails silently. Both were closed by hand: the branch's
docs were served from a throwaway container and the rendered pages driven in a real browser, which
confirmed every heading id, that no in-page anchor is broken, and that the guide's cross-page link
resolves to the new section with status 200.

## 7. Handoff

**What remains: one live walk-through, by a person, in a real Slack workspace.** Everything the
ticket specifies is written and pushed; what is missing is the evidence its Quality Gate asks for.
Two things put it out of this session's reach, both checked rather than assumed:

- Creating the app is a browser session at api.slack.com — there is no API for "create an app and
  install it".
- Reading the workspace already mounted on this machine needs the vault passphrase, which is the
  developer's:

  ```text
  $ qfs run -e "/slack/qmu/general/messages |> select ts, user, text |> limit 3"
  {"error":{"code":"invalid_path","kind":"usage",
            "message":"invalid path \"/slack/qmu/general/messages\": slack_auth", …}}
  ```

To finish it: follow the new section verbatim in a workspace that has no qfs app yet, granting only
`chat:write` and `channels:history`; bind the token; then run a tail read **before** typing
`/invite`, and again after. Record both outcomes here. If either step's Slack label or observable
result differs from what the section says, correct the article — that correction is the point of the
exercise, and the section should not be treated as verified until it happens. The ticket stays in
`.workaholic/tickets/todo/` until then.
