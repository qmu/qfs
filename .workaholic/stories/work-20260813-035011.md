## 1. Overview

`qfs auth` warms a time-boxed unlock of the credential store so later one-shots — another pane, or a
delegated agent's separate processes — skip the passphrase prompt. That window was **8 hours** from
the day the mechanism shipped. The developer asked for **two weeks**, and had asked before; the
earlier telling never became a record, so nothing moved.

**Highlights:**

1. The default window is now **two weeks**, and the ceiling is 30 days so the default is not itself
   clamped.
2. **Two weeks was previously unreachable even with the documented override** — the ceiling was
   seven days and the clamp was silent. `QFS_SESSION_TTL=14d` yielded `7d` and said nothing.
3. A value that is clamped or unparseable is now **stated**, beside the window actually used.

## 2. Motivation

The 8-hour default was chosen when the session cache was built (ticket 20260704170000) and never
revisited. A work-day is the wrong unit for how this machine is used: the operator warms the session
once and delegates one-shot runs to agents over days, so an 8h window means a prompt appears with
nobody there to answer it.

The second finding is the one that mattered more. The documented escape hatch did not work:

```
MAX_TTL_SECS = 7 * 24 * 60 * 60      // the ceiling
QFS_SESSION_TTL=14d qfs auth          // → 7d, silently
```

So an operator who tried to serve themselves got a different window than they asked for, with
nothing in the output saying so. The lost instruction and the silent clamp are the same failure in
two places — a value someone asked for replaced by another without a word — which is why reporting
the adjustment is an acceptance criterion of this change rather than a nicety.

## 3. Changes

### 3-1. Two weeks by default, and every adjustment says so ([8574583](https://github.com/qmu/qfs/commit/8574583))

- `DEFAULT_TTL_SECS` = 14 days; `MAX_TTL_SECS` = 30 days. Each constant's doc comment carries its
  reason: the ceiling exists because the window *is* the value of a stolen `session.unlock` file to
  an attacker holding this uid on this host between reboots — it is a security parameter, not a
  formatting limit.
- `resolve_ttl` now returns the seconds **plus an optional note**, and gained a pure half
  (`resolve_ttl_from`) that takes the raw value, so every rule — default, floor, ceiling, garbage —
  is testable without mutating process environment, which no test can do safely alongside its
  siblings.
- `qfs auth` prints the note beside the session status. Out-of-range values are still clamped and
  unparseable ones still fall back to the default — a session that refused to warm over a typo would
  be worse — but neither happens quietly any more.
- The remaining-time renderer carries days: a fortnight now reads `14d 0h` instead of `336h 0m`.
- `qfs auth --help` and both guide pages state the new window, the new range, and the fact that a
  reboot invalidates the session whatever the TTL says.

**Unchanged, deliberately (developer ruling 2026-08-13):** the session key still folds in the boot
id, so a reboot invalidates the cache. A two-week window therefore means "until the next reboot, at
most two weeks", and the guide says so rather than implying a fortnight of survival.

## 4. Outcome

A bare `qfs auth` warms a two-week session. `QFS_SESSION_TTL=14d` yields exactly two weeks — the
regression that motivated the ticket, now pinned by a test. `QFS_SESSION_TTL=90d` warms 30 days and
says it was clamped and to what; `QFS_SESSION_TTL='two weeks'` warms the default and says the value
was not a duration.

Gates: `cargo test --workspace` 2716 passed / 0 failed (five new hermetic tests), `clippy
--workspace --all-targets -D warnings` clean, `fmt --all --check` clean, `gen-docs` regenerated with
no drift, `gen-skills --check` in sync. Binary bumped to 0.0.97.

## 5. Concerns

### A live session keeps its old deadline, so the change looks inert until `qfs auth` is re-run

- **Severity:** low
- **Description:** The deadline is fixed at mint time and authenticated by the key derivation, so an
  8h session already on disk keeps its 8h deadline (see
  [8574583](https://github.com/qmu/qfs/commit/8574583) in
  `packages/qfs/crates/qfs/src/session_unlock.rs`). Someone who upgrades and checks `qfs vault slots`
  without re-running `qfs auth` will see the old number and reasonably conclude nothing changed.
- **How to Fix:** Nothing in code — the guide now states it. Re-running `qfs auth` mints a fresh
  window.

### The two-week window is nominal on any host that reboots

- **Severity:** low
- **Description:** The boot-id binding, kept by ruling, means the effective window is `min(TTL, time
  until reboot)`. On this long-lived server that is usually the full fortnight; on a laptop it is
  not, and the number printed is still the TTL rather than the effective window (see
  [8574583](https://github.com/qmu/qfs/commit/8574583) in
  `packages/qfs/crates/qfs/src/session_unlock.rs`).
- **How to Fix:** If it ever misleads, `qfs auth` could say "expires in 14d 0h, or at the next
  reboot" — one clause, no behaviour change. Not done here because the guide already states the rule
  and the extra clause on every warm risks reading as noise.

## 6. Successful Development Patterns

- **Making the resolver pure before testing it.** Splitting `resolve_ttl_from(raw)` out of the
  env-reading wrapper turned four rules that could only be exercised by mutating process environment
  — unsafe beside sibling tests — into ordinary table tests. The regression that motivated the whole
  ticket (`14d` → `7d`) is now a two-line assertion.
- **Treating "it said nothing" as the defect, not just "it used the wrong number."** The wrong
  ceiling would have been found in a minute by anyone who read the output, if the output had
  mentioned it. Encoding that as acceptance criteria means the next ceiling change cannot hide the
  same way.

## 7. Release Preparation

**Verdict**: Ready for release

- **Concern:** This lengthens a security window: a cached `session.unlock` is now useful to an
  attacker for up to two weeks rather than eight hours, subject to the unchanged mitigations (0600 +
  uid ownership, the AEAD-authenticated deadline, machine-id and boot-id binding). It is a
  deliberate developer ruling and belongs in the release note in those terms, not as a bare default
  change.
- **After release:** Existing sessions keep their old deadline; run `qfs auth` once after upgrading
  to pick up the new window.
