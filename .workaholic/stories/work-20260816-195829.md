## 1. Overview

`20260812141223` asks for three rulings and their implementation: give an installed declared driver
an identity, give the operator a way to ask whether it is current, and rule whether upgrade is
automatic or operator-initiated. This branch carries the survey those rulings rest on and stops
before the implementation.

## 2. Motivation

The ticket's own step 1 is a ruling, and a ruling made without reading the seams it lands on is the
"unverified inference" the overnight limit names. Four facts change the shape of the answer, and
none of them are visible from the ticket text.

## 4. Outcome

**Two rulings the evidence already settles.**

- **Identity is derived, not stamped.** The ticket proposes recording the installed declaration's
  identity at install time, in the desugar. The desugar sees one `CREATE …` statement at a time and
  never the document, so a whole-script stamp cannot be written there without a side-channel the
  ticket itself forbids. Deriving the identity from the assembled rows instead — canonicalise the
  `DeclaredDriver` model `assemble` already builds and compare it against the same canonicalisation
  of the embedded asset — is both writable and strictly more honest: a stamp is a claim the installer
  makes, a derivation is a fact about what is installed. It also answers the case the ticket flags as
  unhandled, a statement *removed* from the shipped script leaving its row behind, because the
  derived identity differs while a stamp would not. No new row kind and no migration.
- **Upgrade is operator-initiated, never automatic.** Automatic re-install on mismatch is a silent
  write to the operator's System DB performed by a read — `describe` is a pure, cred-free,
  no-I/O surface, and making it mutate config would break the one property every caller relies on.
  Reporting stale and leaving the re-install to the operator keeps the change on the
  previewed-and-committed path where every other config write lives.

**The open question, and why it sizes the change.** The ticket says to reuse an existing surface.
Three candidates were read and none is free:

- `DescribeReport` (`crates/core/src/describe.rs`) carries no free-text or per-mount fact field;
  adding one ripples through every driver's describe output and the gen-docs goldens.
- `driver_catalog` (`crates/qfs/src/catalog.rs`) is deliberately built from the **compiled** registry
  only, so that gen-docs stays a pure function of the binary — a live declared mount may not enter it.
- `/sys/drivers` is a real table, so a derived `declaration` column cannot be added to it.

A fourth option the ticket does not list — a CLI-level fact line rendered beside `describe`, outside
the core report — keeps core untouched and is where the next session should start.

**One more constraint worth knowing before designing:** the workspace carries no hashing crate
(no `sha2`, `blake3`, or equivalent), and blueprint §11 makes adding one a recorded per-dependency
decision. Direct comparison of the canonicalised declaration avoids the question entirely, and over
a handful of statements it is cheaper than the parse the hash would need anyway.

## 8. Notes

The ticket's Considerations already prefer normalising to the parsed statement list over hashing raw
