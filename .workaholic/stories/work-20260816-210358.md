## 1. Overview

Nine `qfs` unit tests resolved the shared `$HOME/.config/qfs` store and tripped its test-build
guard, so `cargo test --workspace` was red on any machine where `XDG_CONFIG_HOME` happened to be
unset. They now carry their own isolated config home.

**Highlights:**

1. `env -u XDG_CONFIG_HOME cargo test --workspace` is green — 2723 passed, previously 9 failed.
2. Three tests swapped the bare env lock for `HomeGuard`; six had no guard at all.
3. The `store.rs` guard is untouched — the tests moved to isolation, the guard did not relax.

## 2. Motivation

`CLAUDE.md` advertises the suite as hermetic, and these nine were hermetic about the network but not
about the environment: their isolation came from whatever the shell happened to export. The defect
is invisible until a container without the variable runs them, where the red gate reads as a fault
in whatever change is being driven — which is exactly how it surfaced, on the previous unit of this
same run.

## 3. Changes

### 3-1. Nine `qfs` unit tests fail on a checkout where `XDG_CONFIG_HOME` is unset ([66b57f4](https://github.com/qmu/qfs/commit/66b57f4))

Three `declared_driver` tests held `env_guard()` — the crate-wide lock without a config home — and
now hold `HomeGuard::new()`, which acquires the same lock and adds the tempdir. Five `sweeper` tests
and one `telemetry` test had no guard and gained one.

## 4. Outcome

The suite is green with the variable unset and with it set, so the result no longer depends on the
shell. `cargo clippy --workspace --all-targets -- -D warnings` and `cargo fmt --all --check` exit 0.

## 5. Successful Development Patterns

- The six unguarded tests did not look like environment tests — `tempdir_host()` isolates host state
  and `build_sink(SinkKind::File)` reads as a pure constructor, yet both reach a store resolver. The
  reliable question is not "does this test touch the environment" but "can anything under it resolve
  a store path", and `HomeGuard` is cheap enough to be the default answer.
