## 1. Overview

`docs/wrangler.toml` stops declaring the two documentation hostnames as `custom_domain` routes, so
a steady-state deploy no longer touches the `qmu.co.jp` zone and the CI token can be narrowed to
account scope. The domains themselves are untouched — they stay attached, out of band.

**Highlights:**

1. A leaked CI token would be bounded to replacing the docs site's content, instead of being able
   to attach a Worker to any hostname on `qmu.co.jp`.
2. Both `workers_dev = false` lines are kept and annotated: without them, removing the routes would
   publish a `workers.dev` hostname for each environment.
3. The deployment record gains the re-attach procedure the config no longer states.

## 2. Motivation

The question asked at the ship of PR #74 was whether the token's zone-scoped permissions were only
needed for the initial setup. They were not. `wrangler` calls `publishCustomDomains` on every
deploy whenever any `custom_domain` route is configured — there is no "already attached, skip"
branch — and a non-TTY run skips the changeset diff and issues an overriding
`PUT …/domains/records`. A configured route also makes each deploy read the zone's worker routes.
`Workers Routes: Edit` cannot be scoped below a whole zone, so as the config stood, the docs-publish
token was permanently able to bind a Worker to any hostname on `qmu.co.jp`, the apex included.

## 3. Changes

## 5. Concerns

### The token is not narrowed until someone swaps the secret

- **Severity:** moderate
- **Description:** This branch removes the *need* for zone scope but cannot remove the *grant*: the
  `CLOUDFLARE_API_TOKEN` repository secret still holds `Zone → Workers Routes → Edit` on
  `qmu.co.jp` until a person replaces it (see
  [db0a1ee](https://github.com/qmu/qfs/commit/db0a1ee) in `docs/wrangler.toml`). Merging alone
  delivers no security benefit, only the declarativeness cost.
- **How to Fix:** Follow the Handoff section: merge, then mint the account-scoped token, replace the
  secret, revoke the wide one.

### A recreated Worker no longer gets its domain back

- **Severity:** low
- **Description:** With the routes gone, a deleted-and-recreated Worker serves nothing on its
  hostname until the custom domain is attached by hand (see
  [db0a1ee](https://github.com/qmu/qfs/commit/db0a1ee) in
  `.workaholic/deployments/docs-site.md`). The tree also no longer states which hostname each
  environment serves in an executable form.
- **How to Fix:** Nothing to change — this is the trade the ticket accepted. The re-attach steps are
  in the deployment record, and re-attaching needs a token with the wide scope the CI secret will no
  longer have.
