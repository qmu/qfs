## 1. Overview

The `qfs` crate's unit suite was green only by scheduling luck: fourteen tests reached a System-DB
opener with no `testenv::HomeGuard`, passing only while a concurrent sibling happened to hold an
isolated `XDG_CONFIG_HOME`. Each now opens its own config home.

**Highlights:**

1. The ticket named one test; the sweep it asked for found fourteen, across six modules.
2. Thirteen were invisible under the default parallel harness — `--test-threads=1` exposed them.
3. Test-only: no production code touched, and the `store.rs` guard deliberately not widened.

## 2. Motivation

`offline_run_engine_does_not_mount_server` called `shell::run_engine_and_reads()` bare, reaching
`store::default_system_db_path()` — which panics in a `cfg(test)` build when `XDG_CONFIG_HOME` is
unset, precisely so a unit test can never touch the shared `$HOME/.config/qfs` and race its
siblings' migration. The test's result was decided by the ambient environment, not the code.

A sweep a day earlier (`20260816205752`, PR #61) closed this class for nine tests and called the
workspace green with the variable unset. It was untrue by more than one test: that sweep read call
graphs, which is what missed `describe_registry()` and `register_cloud_mounts` — entry points whose
names give no hint that a store opener sits under them.

## 3. Changes

### 3-1. Isolate the config home of 14 qfs unit tests ([6ca1924](https://github.com/qmu/qfs/commit/6ca1924))

Every `#[test]` in the `qfs` crate reaching a store opener now binds
`crate::testenv::HomeGuard::new()` first: four in `agent.rs`, four in `job.rs`, two each in
`describe.rs` and `commit.rs`, one in `shell.rs`, and the `provision.rs` test the ticket named — the
guard also takes `ENV_LOCK`, serialising each against the tests whose environment it had borrowed.

## 4. Outcome

`env -u XDG_CONFIG_HOME cargo test -p qfs --lib -- --test-threads=1` reports 519 passed, 0 failed,
against 505 passed / 14 failed before. The workspace suite exits 0 with the variable unset; clippy,
`fmt --check`, `gen-docs --check` and `gen-skills --check` are clean. Patch version `0.0.122`.

## 5. Concerns

### The masking mechanism that hid this class is still in place

- **Severity:** moderate
- **Description:** `HomeGuard` sets `XDG_CONFIG_HOME` process-wide, so a future unguarded test scheduled beside a guarded one inherits its home and passes — the reason thirteen of the fourteen were invisible (see [6ca1924](https://github.com/qmu/qfs/commit/6ca1924) in `packages/qfs/crates/qfs/src/testenv.rs`); CI runs no configuration that would catch the regression.
- **How to Fix:** Add a CI step running `env -u XDG_CONFIG_HOME cargo test -p qfs --lib -- --test-threads=1`, which detected the whole class in one 67-second pass. Demanding per-thread `HomeGuard` ownership in `store.rs` was rejected: tests here reach store openers from threads they did not spawn.

## 6. Successful Development Patterns

- Let an existing assertion do the sweeping: `store.rs:54` was already a perfect detector, so the sweep removed the two conditions that suppress it rather than re-reading call graphs — which is what missed cases last time.
- Read an acceptance criterion's qualifiers as load-bearing: "stays green under `-- --test-threads=1`" was the whole test, and reading it as a restatement would have shipped thirteen live instances.
