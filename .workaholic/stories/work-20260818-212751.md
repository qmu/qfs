## 1. Overview

`select nosuchcol` refused at exit 2 while `select nosuchcol AS x` answered one `null` per row at
exit 0 — two spellings of one question answering two different ways, and the forgiving one the
spelling an operator reaches for. Every spelling now refuses alike.

**Highlights:**

1. The refusal reaches the renaming and computed roads, at both the plan-time and runtime seams.
2. `EXTEND`/`SET` and the late-bound leniency are untouched, each pinned by a test.
3. A shipped declared view's mock was carrying three of the six fields it selects; the leniency was hiding it.

## 2. Motivation

`20260725113000` made a name-only `select` refuse a column the relation does not carry, on the
developer's 2026-07-26 ruling. Both of that ticket's refusals sit on the `Project` road; a
projection that renames or computes lowers to `ProjectExpr` instead, where `eval_value` resolves a
column with `resolve(...).unwrap_or(Value::Null)` and passes neither check.

That ruling's reasoning is what settles this road rather than a fresh judgment: the leniency "was
never a designed affordance, it was the absence of a check", and the absence here is the same one
one function over. The ticket's own recorded policies point the same way, and
`docs/cookbook/faq.md` already claimed `select` refuses an absent column — true of one spelling
only, so leniency required the documentation to stay wrong.

## 3. Changes

### 3-1. Refuse an unknown column in every select form ([c466e83](https://github.com/qmu/qfs/commit/c466e83))

A new `ScalarExpr::col_refs` collector walks the constructor structure, and two seams read it: the
planner refuses against the described schema, the engine over the batch the driver delivered — the
same pair the name-only form has. The check sits at the projection site, never inside `eval_value`,
so `EXTEND`/`SET` keep the total resolution they are meant to have.

## 4. Outcome

The ticket's two commands now answer identically, as do the struct- and array-constructor forms; a
late-bound relation is still never refused. `docs/cookbook/faq.md` and the regenerated `qfs-faq`
skill say so, the plugin's four version fields move to `0.22.0` (a taught surface broke), and the
binary to `0.0.125`. Full gate green.

## 5. Concerns

### A declared view now refuses when its wire response omits a selected field

- **Severity:** moderate
- **Description:** Removing the leniency turned `shipped_chatwork_message_views_build_two_distinct_wire_urls` red: its mock returned three of the six fields the shipped `/chatwork/rooms/{room}/messages` view selects, and the read only worked because the renaming projection resolved the rest to `null` (see [c466e83](https://github.com/qmu/qfs/commit/c466e83) in `packages/qfs/crates/qfs/src/declared_driver.rs`). This is not new in kind — the name-only spelling has refused on that road since `20260725113000` — but it is new in reach, because every shipped view that selects with a rename took the lenient road until now.
- **How to Fix:** The fixture was corrected to return what Chatwork actually returns, including the nested `account` object. If a live API is found to omit a field a shipped view selects, the fix belongs in the declaration (drop the field, or give the view an `OF` contract that states it optional), not in restoring the leniency; the runtime half is one call in `combine.rs` if it must be reverted.

## 6. Successful Development Patterns

- Read a prior ruling for its reasoning, not only its verdict: this fork was recorded as the developer's, but `20260725113000`'s ruling states *why* it refused in terms that name this road exactly, which turned an apparent evidence-free fork into a derivation the run could defend.
- Treat an all-or-nothing lowering fork as a hole in any check added to one arm: `is_plain_projection` routes a whole projection list down the unchecked road as soon as one term carries an alias, so the typo escaping the gate was never the term that looked unusual.
