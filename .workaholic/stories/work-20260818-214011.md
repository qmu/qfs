## 1. Overview

The `qfs` crate's `cfg(test)` guard panics when a unit test resolves the shared
`$HOME/.config/qfs`, but CI ran the suite in the one shape where it cannot fire. `build-test` now
re-runs the lib suite serialised with `XDG_CONFIG_HOME` unset, so a test that forgets its
`HomeGuard` fails every run rather than some.

**Highlights:**

1. Measured with one guard deliberately removed: the parallel run was green 3/3, the serialised run red every time.
2. No production code and no test body changed — the fix is the environment the suite runs in, named in `CLAUDE.md`, the repository guide, the documentation map and `store.rs`.

## 2. Motivation

The guard exists because two tests opening the same on-runner SQLite file race each other's
migration, and it works — it caught nine tests on 2026-08-16 and fourteen more on 2026-08-18. What
it could not do was stay caught: `HomeGuard` sets `XDG_CONFIG_HOME` process-wide, so an unguarded
test passes whenever a guarded sibling is alive, and an ambient `XDG_CONFIG_HOME` suppresses the
guard independently. Under either, `cargo test --workspace` reports whichever way the schedule fell.

The masking runs in the dangerous direction — the more of the class is fixed, the more reliably the
remainder hides behind its correct siblings — which is why the two earlier sweeps read as separate
defects rather than one guard reporting under different conditions.

## 3. Changes

### 3-1. Run the config-home isolation detector in CI ([1541692](https://github.com/qmu/qfs/commit/1541692))

The ticket's first four steps were found already landed in `6ca1924`, so the drive verified them and
spent itself on the fifth: `build-test` gains
`env -u XDG_CONFIG_HOME cargo test -p qfs --lib -- --test-threads=1` as a second step (~70s, no
rebuild after the workspace suite), and the four places a reader looks for the verification surface
now state why the plain suite cannot substitute for it.

## 4. Outcome

The ticket's last acceptance criterion — no test reaches the shared-home fallback whatever the
ambient environment and whatever order the suite runs in — is now held by a check rather than by a
habit. The detector was proven to fail before it was trusted to pass.

## 5. Concerns

### The detector proves the class only for the `qfs` lib target

- **Severity:** low
- **Description:** The new step runs `-p qfs --lib`, because `store.rs`'s guard is `cfg(test)` and so exists in that crate's unit-test build only (see [1541692](https://github.com/qmu/qfs/commit/1541692) in `.github/workflows/ci.yml`). Integration tests and other crates keep the real `HOME` fallback deliberately, so nothing states what config home they open.
- **How to Fix:** If a later integration test starts touching the store, give it the same isolation seam rather than widening this step, and record which target owns the guarantee.

## 6. Successful Development Patterns

- Break the guard on purpose before trusting it: removing one `HomeGuard` turned "the serialised run should catch this" into a measurement (parallel 3/3 green, serialised red every time), and it cost two suite runs.
- Ship a test-hygiene guard together with the run that makes it fire — a `cfg(test)` panic is only as strong as the weakest environment anyone actually runs.

## 7. Notes

The rejected alternative is recorded in the ticket's Final Report: a thread-aware `HomeGuard` would
catch the class without a serialised run, but tests in this crate reach store openers from threads
they did not spawn, so thread locality would produce false panics.
