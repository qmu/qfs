## 1. Overview

This branch started as an unattended run's third "still blocked" note on
`20260817131540-file-the-bun-plgg-md-parse-defect-upstream`, and was taken over by a developer
session. Both of the blockers holding that ticket turned out to be assumptions nobody had probed,
and the ticket closes here with all four of its steps met.

**Highlights:**

1. `qmu/plgg` is a **public** repository, not the private one the ticket's `verification_handoff:`
   and its two blocked entries assumed. The upstream issue is filed:
   [qmu/plgg#131](https://github.com/qmu/plgg/issues/131).
2. The parse defect was **bun's**, and **bun fixed it in 1.3.13** — measured against an unchanged
   `plgg-md@0.0.3`. The wait was never on `plgg-md` being republished.
3. The npx smoke's bun exemption is gone; the gate passes with node, bun and deno all covered and
   no `NOT COVERED` line, and CI now installs all three.

## 2. Motivation

The ticket was recorded blocked on 2026-08-17 and re-dated twice, on 2026-08-18 and again later that
night. Each entry was careful, dated and honest about what it ran — and each rested on two premises
that were never checked. The first was that `qmu/plgg` is private and unreachable, which one
`gh repo view` disproves. The second was the shape of the wait: steps 3 and 4 were recorded as
blocked on *someone publishing a fixed `plgg-md`*, and every run duly re-checked
`npm view plgg-md versions`, found `0.0.3` still newest, and concluded nothing had moved.

But the exemption in `smoke-npx.sh` named **two** release conditions, not one: "REVISIT AFTER
2026-11-17, **or as soon as a bun release parses the published dist**." Only the package half was
ever re-checked. The runtime half had already fired.

What actually unblocked this was the machine. The unattended containers had bun 1.3.11 and no deno;
the developer host has node v24.13.1, bun 1.3.14 and deno 2.9.2 — the whole matrix the product
promises, which is exactly what the ticket needed to be measured against.

## 3. Changes

### 3-1. Retire the bun exemption, bun 1.3.13 fixed it ([36c7794](https://github.com/qmu/qfs/commit/36c7794))

Probed each bun version with its own official release binary, running an `import()` of
`plgg-md/dist/index.es.js` — not inferred from a changelog:

| Runtime | Result |
| --- | --- |
| bun 1.3.11 | `SyntaxError: Invalid regular expression: range out of order in character class` |
| bun 1.3.12 | same `SyntaxError` |
| **bun 1.3.13** | **parses** |
| bun 1.3.14 | parses |
| node v24.13.1 | parses |
| deno 2.9.2 | parses |

The package is unchanged throughout — `plgg-md@0.0.3` is still `dist-tags.latest`, its dist still
contains the literal NUL and still emits the class with raw endpoints at offset 61336. So the fault
was bun's lexer and bun shipped the fix.

- `packages/qfs-viewer/scripts/smoke-npx.sh` — the exemption is replaced by the measured version
  floor. The same narrow signature match now **fails** with "fixed in bun 1.3.13 — upgrade" rather
  than reporting `NOT COVERED`, because an old local bun is a fixable local condition and not an
  upstream wait. bun counts in `RAN` again.
- `.github/workflows/ci.yml` — `viewer-check-all` installs bun and deno alongside Node 24, so a
  green badge stops attesting to node alone.
- `packages/qfs-viewer/README.md`, `docs/guide/repository.md` — the bun-is-broken caveat is retired
  and the history kept as history, so a reader meeting an old bun still finds the explanation.

### 3-2. Close the bun plgg-md ticket, all four steps ([e8ada6e](https://github.com/qmu/qfs/commit/e8ada6e))

The ticket is archived carrying a Final Report that gives each of its four steps a measured outcome
and the command behind every claim.

## 4. Outcome

`npx qfs-viewer` is demonstrated working under all three runtimes the product promises, on a machine
that has all three, with nothing exempted. Before this branch the gate proved node and said out loud
that it could not speak for bun; now `cd packages/qfs-viewer && ./scripts/check-all.sh` exits `0`
with `PASS: node …`, `PASS: bun …`, `PASS: deno …` and zero `NOT COVERED` lines, and CI runs the same
matrix rather than node alone.

A developer whose bun is older than 1.3.13 is not silently uncovered any more — the gate fails and
tells them the floor and the fix.

## 5. Concerns

### CI gained two third-party setup actions

- **Severity:** low
- **Description:** `viewer-check-all` previously used only `actions/*`. Installing bun and deno adds
  `oven-sh/setup-bun@v2` and `denoland/setup-deno@v2` — each the runtime's own org, and both pinned
  to a major tag rather than a commit SHA. That is a new supply-chain surface in a workflow that had
  none, and it is worth a deliberate nod rather than arriving as a side effect of a docs ticket.
- **How to Fix:** Pin both to commit SHAs if the repository decides workflow actions should be
  SHA-pinned; otherwise accept them as the canonical installers.

### The upstream build wart is real and stays open

- **Severity:** low
- **Description:** `plgg-md`'s bundler still emits the control-character class endpoints as raw bytes
  rather than escaped. It no longer breaks any runtime, but the embedded NUL still makes `grep`
  classify the shipped dist as binary, and a future lexer could trip on it the way bun did.
- **How to Fix:** [qmu/plgg#131](https://github.com/qmu/plgg/issues/131) is open and carries the ask.
  Nothing in this repository waits on it.

## 6. Successful Development Patterns

**An exemption should name its release condition, not just a date.** This one named both. The date
was 2026-11-17 and would have held the debt three months past the fix; the condition it also named
fired within two days. The condition is what made the exemption cheap to retire — and re-reading the
exemption's own text is what found it.

**Probe the assumption under a blocker, not only the blocker.** Three runs re-ran
`npm view plgg-md versions` faithfully and none ran `gh repo view qmu/plgg`. The premise that went
unchecked was the one that was wrong, twice over: the repository was public, and the wait was on the
runtime rather than the package.

**Measure on a machine that resembles the target.** The container could not represent the runtime
matrix the product promises, so every honest measurement it made was also a measurement of the wrong
thing.
