## 2. Motivation

The ticket's step 4 asks for one command: `curl -sS https://staging-qfs.qmu.co.jp/version.json`
reports the new merge commit. Three unattended runs could not run it — outbound HTTPS to both
hostnames returned `curl: (56) CONNECT tunnel failed, response 403` — and each fell back to reading
the merge's workflow run instead.

That substitute is weaker than the check it replaced, and weaker in exactly the direction the routes
removal is risky in. Removing `routes` from `docs/wrangler.toml` stops the deploy re-asserting the
custom domains; if a domain ever came unattached, the publish job would still go green, because
publishing a Worker and a hostname pointing at it are different facts. Only the hostname answering
proves the second one.

The 403 is also worth naming for what it is: a property of those containers' egress proxy, not of
the deployment. Recorded three times without that qualification, it was on its way to becoming a
fact about the site.

## 5. Concerns

### The docs CI token still holds zone-wide Workers Routes

- **Severity:** moderate
- **Description:** `CLOUDFLARE_API_TOKEN` is still the token minted with `Zone → Workers Routes:
  Edit` on `qmu.co.jp`, so a leak from GitHub Actions can bind a Worker to any hostname in the zone,
  the apex included. The repository-side work that made narrowing possible landed in
  [db0a1ee](https://github.com/qmu/qfs/commit/db0a1ee); the token itself has not moved.
- **How to Fix:** Mint a replacement holding only `Account → Workers Scripts: Edit` and
  `Account → Account Settings: Read`, swap the repository secret, revoke the wide token.

### Staging's non-indexability rests on one mechanism, not two

- **Severity:** low
- **Description:** The design intended `robots.txt` and `X-Robots-Tag` as two independent guards.
  While the zone's Cloudflare managed robots.txt is on, only the header binds. It is the stronger of
  the two and it is present, so staging is protected — but a single point of failure was documented
  as a pair.
- **How to Fix:** Either turn off the zone's managed robots.txt, which restores the origin
  `Disallow: /`, or accept the header as the single guard and keep the record saying so plainly (this
  branch does the latter).

## 6. Successful Development Patterns

**Check the deployed artifact, not the generator.** `stamp-docs-deploy.sh` writes a correct staging
`robots.txt`, and reading it would have confirmed the guard. What the world receives is that file
with a Cloudflare block prepended, and only `curl` against the hostname shows it.

**A blocked check's failure mode deserves a label.** "`curl` → 403" recorded without "in this
container" was three days from being read as "the hostnames are unreachable".
