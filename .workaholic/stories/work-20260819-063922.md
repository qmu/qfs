## Handoff

**Three console acts on the docs-deploy token remain, and two of them are genuinely the account
holder's.** The retry loop this branch was opened to stop is now stopped durably rather than only
while this pull request stays open.

- **Done:** `verification_handoff:` is set on the ticket — the disposition this branch measured its
  way to and was forbidden from applying to itself. Plus the correction below.
- **Not done:** minting the narrow Cloudflare token and revoking the wide one. Both need a
  credential holding `User → API Tokens: Edit`.
- **Note:** replacing the repository secret — act 2 of the three — is *not* a dashboard act and can
  be done from a developer session with `gh secret set`.

## 1. Overview

An unattended run opened this branch after four runs had each claimed the Cloudflare docs-token
ticket, re-blocked it and opened a pull request saying so. It diagnosed the loop correctly: the
ticket asks for work no runner can perform and, it argued, no runner can even observe. It then named
the fix — set `verification_handoff:` — and recorded that a drive run may not write that field for
itself. This takeover applies the fix and scopes the finding.

**Highlights:**

1. `verification_handoff:` is set, so an unattended unit takes the declared-handoff route on sight
   and the ticket stops being re-offered every survey — independently of this pull request's state.
2. The 403 the branch rests on is the **unattended session's proxy**, not GitHub: from a developer
   session `gh secret list` and `actions/secrets/public-key` both answer.
3. So the swap is both observable (`updated_at` moves) and performable here (`gh secret set`). Only
   minting and revoking still need the Cloudflare dashboard.

## 2. Motivation

The branch's own Concerns section names the flaw in its remedy: parking the claim behind an open
pull request holds the loop only while the pull request is open, and merging or closing it without
acting hands the ticket back to the next tick. It could not fix that itself — `workaholic:drive` §6
forbids a drive run from writing `verification_handoff:` mid-drive, deliberately, since a runner that
can declare its own work un-verifiable can excuse anything. A developer session is exactly what that
rule defers to, so the recommendation was waiting for this and nothing else.

The second half is a recurring failure on this one ticket. Its 2026-08-19 entry corrected a
`curl: (56) CONNECT tunnel failed, response 403` that three runs had recorded as a fact about the
docs hostnames when it was a fact about their egress proxy. This branch then recorded
`gh api repos/qmu/qfs/actions/secrets` → 403 as a fact about the API, and built "there is no green
signal an unattended tick can wait for" on it. Same shape, four days apart.

## 4. Outcome

The queue stops re-offering a ticket no unattended run can finish, which is what the four prior
pull requests were each a symptom of. A developer picking the ticket up now reads which act is which:
one `gh secret set` from a session like this one, two visits to the Cloudflare dashboard, and an
acceptance check that costs a single API call.

Nothing about the exposure changes. `CLOUDFLARE_API_TOKEN` still holds zone-wide
`Workers Routes: Edit` on `qmu.co.jp`.

## 6. Successful Development Patterns

**A refusal is evidence about the session that got it.** Twice on this ticket a proxy 403 was
written down as a property of the world — once about the docs hostnames, once about the GitHub
Actions API — and both times the conclusion drawn from it was stronger than the measurement
supported. Naming the session inside the finding is what keeps it from outliving the session.

**A runner that diagnoses its own loop should not also be trusted to exempt itself from it.** The
rule that stopped this branch writing `verification_handoff:` is why the diagnosis is worth reading:
it had to convince a person instead of dismissing the work. The cost is that the fix waits for a
developer — which is the correct price.
