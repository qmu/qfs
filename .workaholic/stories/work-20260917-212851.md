## 1. Overview

`/moderate` writes its tick log to an untracked `.workaholic/moderations/`, and the freshen
opening every `[Implement]` tick refuses an untracked path as `dirty_workspace` — so each
maintenance tick left behind exactly the state that stopped the next implementation tick.

**Highlights:**

1. `.gitignore` gains `.workaholic/moderations/`, with a comment recording why it is deliberate.
2. The committed rule outranks the local-only `.git/info/exclude` unblock, so it is provably live.
3. `qfs` patch version raised to `0.0.136` per the repository's per-PR bump rule.

## 2. Motivation

Two contracts were each correct and jointly deadlocking. `/moderate`'s `persist-log` step
states that leaving its tick log untracked is intent; `sync-main.sh` refuses any unclean tree,
and `check-workspace.sh` counts an untracked path as dirty. The rescue,
`clear-proved-residue.sh`, refuses `untracked_present` by design — a file on no ref is covered
by no proof. The loop therefore disabled itself on a schedule, the shape of the 2026-09-08
`clear-the-residue-the-base-already-holds-and-never-stop-silently` mission (21 ticks, ~100
idle minutes). Neither script can be widened from here — both are the plugin's, both refusals
deliberate.

## 3. Changes

### 3-1. Ignore the /moderate tick-log directory so the [Implement] freshen stops refusing ([3a6e12f](https://github.com/qmu/qfs/commit/3a6e12f))

Adds `.workaholic/moderations/` to `.gitignore`, in the `.workaholic` area beside the existing
`.workaholic/leak-denylist` entry, with a comment explaining that `/moderate` deliberately
leaves the tick log untracked and that without the entry every freshen refuses. No other file
in the repository changes behaviour.

## 4. Outcome

The freshen passes with a tick log present, and `/moderate`'s log stays in the checkout as its
contract intends. The fix also travels: the local exclude unblocked one checkout, the
committed line reaches every clone.

## 5. Concerns

### The local-only .git/info/exclude unblock still shadows the committed rule

- **Severity:** low
- **Description:** `/home/ec2-user/projects/qfs/.git/info/exclude` on the development server still carries the same `.workaholic/moderations/` line that this branch commits to `.gitignore` (see [3a6e12f](https://github.com/qmu/qfs/commit/3a6e12f) in `.gitignore`). Two sources for one rule can silently diverge, and the local one would keep that checkout working even if the committed line were later broken.
- **How to Fix:** Remove the two comment lines and the `.workaholic/moderations/` line from `.git/info/exclude` on that server once this merges, so the committed entry is the only thing holding the checkout clean. Ticket step 5 names this and it is deliberately not done inside the branch that proposes the fix.

### Thirty-six deferred concerns were carried rather than judged

- **Severity:** low
- **Description:** `list-open-concerns.sh` reports 36 open deferred concerns on this repository. This run left every one `still_active` without individually re-judging it: the branch touches only `.gitignore` and supplies no evidence for resolving anything, and the subagent fan-out the judge phase normally uses was unavailable to this run.
- **How to Fix:** Let a later `/story` run on a substantive branch judge the set with the ordinary Phase 1 fan-out; the safe direction is already taken, so nothing is lost beyond the concerns staying open one cycle longer.

## 6. Successful Development Patterns

- Reproducing a shared-checkout failure in a throwaway repository rather than by mutating the checkout's own `.git/info/exclude` — that file is shared by every worktree, so the obvious reproduction would have made a concurrent session's freshen fail for real.
- Reading `git check-ignore -v` as the acceptance probe: because git ranks `.gitignore` above `.git/info/exclude`, the output names which rule actually matched, which proves the committed line is live without removing the local one first.
